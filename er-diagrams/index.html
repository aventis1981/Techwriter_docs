    ER-диаграммы (нотация)

    ER-диаграмма

    ER-диаграмма (от англ. Entity-Relationship Diagram — диаграмма «сущность-связь») — это графическая схема, которая наглядно показывает, какие данные есть в системе и как они связаны между собой.

    • Сущность (Entity) — это «объект», про который мы храним данные. В терминах БД — это таблица (collection, object)
    • Атрибут (Attribute) — характеристика сущности. В БД — колонка таблицы (id, data)
    • Первичный ключ (PK, Primary Key) — уникальный идентификатор строки. Без него нельзя однозначно обратиться к записи.
    • Внешний ключ (FK, Foreign Key) — ссылка на PK другой таблицы. Показывает связь.
    • Связь (Relationship) — как сущности «относятся» друг к другу («одна коллекция содержит много объектов»).
    • Кардинальность — сколько экземпляров одной сущности связано с экземпляром другой («Один ко многим» (1:N): одна коллекция → много объектов).

    Сущность - Collection

    • id (PK) - технический ключ, используется внутри БД для связей
    • name (unique key) - бизнес-ключ, видимый в API
    • owner_id - владелец (важно для прав доступа)
    • created_at - дата создания

    Сущность - Object

    • id (PK) — уникальный идентификатор объекта
    • collection_id (FK) - техническая связь. Гарантирует, что объект принадлежит существующей коллекции. API использует name для адресации, но в БД связь идёт через id. ER-диаграмма показывает внутреннюю структуру (через ID), а не внешний интерфейс (через name)
    • name - имя объекта
    • data - произвольные данные
    • updated_at - дате обновления

    Одна коллекция содержит множество объектов. В restful-api.dev коллекция не создаётся и не удаляется напрямую: она появляется при создании первого объекта и исчезает при удалении последнего. “Автоудаление коллекции” — это бизнес-правило приложения, а не CASCADE в БД: удаление инициируется кодом API при проверке количества объектов, а не механизмом базы данных. Поэтому на ER-диаграмме это показывается как заметка, а не как тип связи. Каскадное удаление (ON DELETE CASCADE) — это строго «родитель удаляется → дети удаляются», а здесь обратная логика.

    Теория

    Базовые «кирпичики» (что значит каждый символ):

    • || — «одна и только одна». Обязательная связь: у объекта обязательно должна быть ровно одна связанная запись. Пример: у каждого OBJECT обязательно есть одна COLLECTION.
    • | — просто «одна». Связь есть, и она одна, но в некоторых нотациях может означать «может быть одна, а может и не быть» — в Mermaid чаще именно обязательность дают через ||.
    • o — «ноль или больше». Связи может вообще не быть, а может быть сколько угодно.
    • { — «один или больше». Связи не может не быть — минимум одна, а дальше сколько угодно.

    Комбинации: - ||--|| — «одна к одной, обе стороны обязательны». У каждой записи ровно одна пара, и у пары ровно одна запись. Например, у пациента ровно одна медицинская карта, карта связана строго с одним пациентом. - ||--o{ — «одна и только одна — ноль или более». Это «один ко многим» с обязательной связью: одна COLLECTION может иметь 0, 1, 100 объектов, но каждый OBJECT обязан принадлежать ровно одной коллекции. Это самый частый вариант. - o--o — «ноль или более к нулю или более». Связи может не быть вообще ни у кого, а может быть много у обоих. Часто используют, когда связь необязательна с обеих сторон. - {--{ — «один или более к одному или более». Связь точно есть (минимум одна), и может быть много с обеих сторон — это уже «многие ко многим».

    1 Обязательная связь "один к одному"

    erDiagram
    PATIENT ||--|| MEDICAL_CARD : "имеет"

    PATIENT {
        id 
        first_name
        last_name
        birth_date
        email
    }

    MEDICAL_CARD {
        id
        date_of_creation
        date_of_update
        patient_id
    }

    Связь: PATIENT ||--|| MEDICAL_CARD : "имеет"

    Это строгая связь «один к одному» с обязательностью с обеих сторон:

    • PATIENT ||: каждый пациент имеет ровно одну медицинскую карту в организации (больнице). Нельзя создать пациента без мед.карты.
    • || MEDICAL_CARD: каждая медицинская карта может принадлежать только одному пациенту. Недопустимы orphan records (записи-сироты): каждая медицинская карта обязана быть привязана к пациенту.

    Почему это важно для целостности данных:
    Нотация ||--|| фиксирует бизнес-правило: сущность не существует без своей пары. Это предотвращает ситуации, когда в базе есть «висячие» медицинской карты или пациенты без карты.

    Реализация в физической модели: Хотя в ER-диаграмме Mermaid внешний ключ не пишется явно внутри блока атрибутов, связь ||--|| подразумевает наличие обязательного FK. Чаще всего его размещают в таблице «карты», так как карта — это дополнительная информация к основному объекту.

    Таблица: MEDICAL_CARD (реализация связи):

    Поле Тип Ограничения Описание
    id INT PK Уникальный идентификатор медицинской карты
    date_of_creation DATETIME NOT NULL Дата создания медицинской карты
    date_of_update DATETIME NOT NULL Дата последнего обновления медицинской карты
    patient_id INT NOT NULL, UNIQUE, FK → PATIENT.id Обязательный и уникальный внешний ключ, однозначно связывающий медицинскую карту с пациентом. Гарантирует отношение 1:1
    • NOT NULL гарантирует, что карта не может быть «бесхозной».
    • UNIQUE гарантирует, что у одного пациента не будет двух медицинских карт.

    Ключевые моменты реализации: - patient_id как UNIQUE: это техническое решение, которое превращает связь «один ко многим» (обычный FK) в «один к одному». - Обязательность (NOT NULL): соответствует двойным палочкам || в нотации.

    Пример использования в API:

    Такая модель позволяет строить предсказуемые эндпоинты:

    • GET /patients/{id}/medical-card — возвращает объект medicalCard (200 OK) либо 404 Not Found, если пациента нет. Отсутствие медицинской карты у существующего пациента трактуется как нарушение бизнес‑правила и не должно приводить к ответу 200 OK с пустым телом.
    • POST /patients — при создании пациента (POST /patients) бизнес-логика требует одновременного создания медицинской карты. Альтернативно — пациент создаётся в статусе DRAFT, а карта должна быть создана до перевода в статус ACTIVE.

    Для разработчика:

    Поле patient_id в таблице MEDICAL_CARD является обязательным внешним ключом с уникальным ограничением. Это обеспечивает строгое соответствие один к одному между сущностями PATIENT и MEDICAL_CARD. В ответах API медицинская карта всегда присутствует как вложенный объект или отдельный ресурс с гарантированным не-null идентификатором пациента. Создание пациента и его медицинской карты рекомендуется выполнять в рамках одной транзакции либо гарантировать атомарность через бизнес-логику, чтобы избежать состояния “пациент без карты”»

    1 Один ко многим

    erDiagram
    USER ||--o{ POST : "пишет"
    CATEGORY ||--o{ POST : "содержит"

    USER {
        id PK
        email
        nickname
    }

    POST {
        id PK
        title
        content
        published_at
    }

    CATEGORY {
        id PK
        name
        description
    }

    Связь USER–POST Это связь “один ко многим” (||--o{). Один пользователь может иметь ноль или более постов, но каждый пост строго принадлежит ровно одному пользователю. Это гарантирует целостность данных: пост не может существовать без автора, а автор однозначно определён через внешний ключ user_id.

    Связь CATEGORY–POST Здесь тоже связь “один ко многим”. Одна категория может содержать ноль или более постов, при этом каждый пост относится ровно к одной категории. Такое решение упрощает фильтрацию по категориям на уровне API (например, GET /posts?category_id=...) и позволяет легко строить отчёты “посты в категории”.

    erDiagram
    CUSTOMER ||--o{ ORDER : "делает"

    CUSTOMER {
        id PK
        name
        email
    }

    ORDER {
        id PK
        amount
        status
    }

    Также связь “один ко многим” (||--o{). В рамках этой модели у одного клиента может быть ноль или более заказов, при этом каждый заказ обязательно принадлежит ровно одному клиенту. Обязательность со стороны заказа (двойные палочки || у CUSTOMER) гарантирует целостность данных: не бывает “бесхозных” заказов без клиента. Для реализации это значит, что в таблице ORDER будет внешний ключ customer_id, по которому легко получить все заказы конкретного клиента (например, через GET /customers/{id}/orders) либо найти клиента по заказу

    2 Необязательная связь "ноль ко многим" с обеих сторон

    erDiagram
    EMPLOYEE o--o PROJECT : "участвует в"

    EMPLOYEE {
        id PK
        name
    }

    PROJECT {
        id PK
        title
        status
    }

    Это связь “ноль ко многим” с обеих сторон (o--o). В рамках этой модели сотрудник может участвовать в нуле или множестве проектов, а проект может включать ноль или множество сотрудников. Отсутствие двойных палочек (||) означает, что связь необязательна: сотрудник может существовать в системе без привязки к проектам, а проект — без назначенных сотрудников. На практике такую модель используют на ранних этапах или для гибких ролей, когда участие не является обязательным атрибутом сущности

    «В ER-диаграмме показана логическая связь o--o для наглядности, но в реляционной БД “многие ко многим” реализуют через связующую таблицу. Так мы сохраняем нормализацию и можем хранить дополнительные атрибуты связи — например, роль сотрудника в проекте или дату назначения».

    3 Обязательная связь «один к одному или многим»

    erDiagram
    TEAM ||--{ DEVELOPER : "работает в"

    TEAM {
        id PK
        name
    }

    DEVELOPER {
        id PK
        name
        email
    }

    Связь: TEAM ||--{ DEVELOPER : "включает"

    Описание:
    Это связь «один ко многим» с обязательным участием с обеих сторон: - Со стороны TEAM (||): каждая команда обязана включать одного или более разработчиков. Пустых команд в системе быть не может. - Со стороны DEVELOPER ({): каждый разработчик обязан состоять ровно в одной команде. Работа без команды или одновременная работа в нескольких командах невозможна.

    Целостность данных:
    Обязательность связи обеспечивается на уровне БД через: - NOT NULL для внешнего ключа team_id в таблице DEVELOPER (разработчик не может существовать без команды). - Бизнес-правило или триггер на стороне приложения: нельзя создать команду без хотя бы одного разработчика.

    Практическое применение в API:
    Такая модель позволяет уверенно строить эндпоинты вида: - GET /teams/{team_id}/developers — получить всех разработчиков команды (гарантированно будет хотя бы один). - GET /developers/{id} — в ответе всегда будет поле teamId, которое никогда не будет null.

    Реализация связи в физической модели

    Хотя на ER-диаграмме внешний ключ не отображается явно, связь TEAM ||--{ DEVELOPER подразумевает наличие обязательного внешнего ключа в таблице DEVELOPER.

    Таблица: DEVELOPER
    Поле Тип Ограничения Описание
    id INT PK Уникальный идентификатор разработчика
    name VARCHAR(255) NOT NULL Имя разработчика
    email VARCHAR(255) UNIQUE, NOT NULL Email разработчика
    team_id INT NOT NULL, FK → TEAM.id Обязательная ссылка на команду. Гарантирует, что разработчик всегда принадлежит ровно одной команде
    Важные ограничения БД
    • NOT NULL на team_id: разработчик не может существовать без команды.
    • Внешний ключ (FOREIGN KEY) с каскадом RESTRICT или NO ACTION: нельзя удалить команду, пока в ней есть разработчики (это поддерживает правило «в команде должен быть хотя бы один разработчик» на уровне БД).
