## ER-диаграмма

>ER-диаграмма (от англ. Entity-Relationship Diagram — диаграмма «сущность-связь») — это графическая схема, 
>которая наглядно показывает, какие данные есть в системе и как они связаны между собой. 

> - Сущность (Entity) — это «объект», про который мы храним данные. В терминах БД — это таблица (*collection*, *object*)
> - Атрибут (Attribute) — характеристика сущности. В БД — колонка таблицы (*id*, *data*)
> - Первичный ключ (PK, Primary Key) — уникальный идентификатор строки. Без него нельзя однозначно обратиться к записи.
> - Внешний ключ (FK, Foreign Key) — ссылка на PK другой таблицы. Показывает связь.
> - Связь (Relationship) — как сущности «относятся» друг к другу («одна коллекция содержит много объектов»).
> - Кардинальность — сколько экземпляров одной сущности связано с экземпляром другой («Один ко многим» (1:N): одна коллекция → много объектов).

**Сущность - Collection**

- id (PK) - технический ключ, используется внутри БД для связей
- name (unique key) - бизнес-ключ, видимый в API
- owner_id - владелец (важно для прав доступа)
- created_at - дата создания

**Сущность - Object**

- id (PK) — уникальный идентификатор объекта
- collection_id (FK) - техническая связь. Гарантирует, что объект принадлежит существующей коллекции.
API использует name для адресации, но в БД связь идёт через id. 
ER-диаграмма показывает внутреннюю структуру (через ID), а не внешний интерфейс (через name)
- name - имя объекта
- data - произвольные данные
- updated_at - дате обновления

>Одна коллекция содержит множество объектов. В restful-api.dev коллекция не создаётся и не удаляется напрямую: она появляется при создании первого объекта и исчезает при удалении последнего. 
>“Автоудаление коллекции” — это бизнес-правило приложения, а не CASCADE в БД: удаление инициируется кодом API при проверке количества объектов, а не механизмом базы данных. Поэтому на ER-диаграмме это показывается как заметка, а не как тип связи.
>Каскадное удаление (ON DELETE CASCADE) — это строго «родитель удаляется → дети удаляются», а здесь обратная логика.

## Теория

Базовые «кирпичики» (что значит каждый символ)
|| — «одна и только одна». Обязательная связь: у объекта обязательно должна быть ровно одна связанная запись.
Пример: у каждого OBJECT обязательно есть одна COLLECTION.
| — просто «одна». Связь есть, и она одна, но в некоторых нотациях может означать «может быть одна, а может и не быть» — в Mermaid чаще именно обязательность дают через ||.
o — «ноль или больше». То есть связи может вообще не быть, а может быть сколько угодно.
{ — «один или больше». Связи не может не быть — минимум одна, а дальше сколько угодно.
Готовые комбинации (то, что реально встречается на собеседованиях)
||--o{ (как у тебя в диаграмме) — «одна и только одна — ноль или более».
Это «один ко многим» с обязательной связью: одна COLLECTION может иметь 0, 1, 100 объектов, но каждый OBJECT обязан принадлежать ровно одной коллекции. Это самый частый вариант.
||--|| — «одна к одной, обе стороны обязательны».
У каждой записи ровно одна пара, и у пары ровно одна запись. Например, у пользователя ровно один профиль, у профиля ровно один пользователь.
o--o — «ноль или более к нулю или более».
Связи может не быть вообще ни у кого, а может быть много у обоих. Часто используют, когда связь необязательна с обеих сторон.
{--{ — «один или более к одному или более».
Связь точно есть (минимум одна), и может быть много с обеих сторон — это уже «многие ко многим».

### 1 Многие ко многим

```mermaid
erDiagram
    USER ||--o{ POST : "пишет"
    CATEGORY ||--o{ POST : "содержит"

    USER {
        id PK
        email
        nickname
    }

    POST {
        id PK
        title
        content
        published_at
    }

    CATEGORY {
        id PK
        name
        description
    }

```
**Связь USER–POST**
Это связь “один ко многим” (||--o{). Один пользователь может иметь ноль или более постов, но каждый пост 
строго принадлежит ровно одному пользователю. Это гарантирует целостность данных: 
пост не может существовать без автора, а автор однозначно определён через внешний ключ user_id.

**Связь CATEGORY–POST**
Здесь тоже связь “один ко многим”. Одна категория может содержать ноль или более постов, 
при этом каждый пост относится ровно к одной категории. Такое решение упрощает фильтрацию по 
категориям на уровне API (например, GET /posts?category_id=...) и позволяет легко строить отчёты “посты в категории”.


### 2 "Ноль ко многим" с обеих сторон

``` mermaid
erDiagram
    EMPLOYEE o--o PROJECT : "участвует в"

    EMPLOYEE {
        id PK
        name
    }

    PROJECT {
        id PK
        title
        status
    }
```
	
>Это связь “ноль ко многим” с обеих сторон (o--o). В рамках этой модели сотрудник может участвовать в нуле 
>или множестве проектов, а проект может включать ноль или множество сотрудников. 
>Отсутствие двойных палочек (||) означает, что связь необязательна: сотрудник может существовать в системе без привязки к проектам, а проект — без назначенных сотрудников. На практике такую модель используют на ранних этапах или для гибких ролей, 
>когда участие не является обязательным атрибутом сущности

>«В ER-диаграмме показана логическая связь o--o для наглядности, но в реляционной БД “многие ко многим” реализуют через связующую таблицу. 
>Так мы сохраняем нормализацию и можем хранить дополнительные атрибуты связи — например, 
>роль сотрудника в проекте или дату назначения».


### 3 Один ко многим

```mermaid
erDiagram
    CUSTOMER ||--o{ ORDER : "делает"

    CUSTOMER {
        id PK
        name
        email
    }

    ORDER {
        id PK
        amount
        status
    }
```

>Это связь “один ко многим” (||--o{). В рамках этой модели у одного клиента может быть ноль или более заказов, 
>при этом каждый заказ обязательно принадлежит ровно одному клиенту. Обязательность со стороны заказа (двойные палочки || у CUSTOMER) 
>гарантирует целостность данных: не бывает “бесхозных” заказов без клиента. Для реализации это значит, 
>что в таблице ORDER будет внешний ключ customer_id, по которому легко получить все заказы конкретного клиента 
>(например, через GET /customers/{id}/orders) либо найти клиента по заказу

### 4 Обязательная связь «один к одному или многим»

```mermaid
erDiagram
    TEAM {
        id PK
        name
    }

    DEVELOPER {
        id PK
        name
        email
    }
```

**Связь:** `TEAM ||--{ DEVELOPER : "включает"`

**Описание:**  
Это связь «один ко многим» с обязательным участием с обеих сторон:
- **Со стороны TEAM (`||`)**: каждая команда обязана включать **одного или более** разработчиков. Пустых команд в системе быть не может.
- **Со стороны DEVELOPER (`{`)**: каждый разработчик обязан состоять ровно в **одной** команде. Работа без команды или одновременная работа в нескольких командах невозможна.

**Целостность данных:**  
Обязательность связи обеспечивается на уровне БД через:
- `NOT NULL` для внешнего ключа `team_id` в таблице `DEVELOPER` (разработчик не может существовать без команды).
- Бизнес-правило или триггер на стороне приложения: нельзя создать команду без хотя бы одного разработчика.

**Практическое применение в API:**  
Такая модель позволяет уверенно строить эндпоинты вида:
- `GET /teams/{team_id}/developers` — получить всех разработчиков команды (гарантированно будет хотя бы один).
- `GET /developers/{id}` — в ответе всегда будет поле `teamId`, которое никогда не будет `null`.

#### Реализация связи в физической модели

Хотя на ER‑диаграмме внешний ключ не отображается явно, связь `TEAM ||--{ DEVELOPER` подразумевает наличие обязательного внешнего ключа в таблице `DEVELOPER`.

##### Таблица: DEVELOPER
| Поле | Тип | Ограничения | Описание |
| --- | --- | --- | --- |
| id | INT | PK | Уникальный идентификатор разработчика |
| name | VARCHAR(255) | NOT NULL | Имя разработчика |
| email | VARCHAR(255) | UNIQUE, NOT NULL | Email разработчика |
| team_id | INT | NOT NULL, FK → TEAM.id | Обязательная ссылка на команду. Гарантирует, что разработчик всегда принадлежит ровно одной команде |

##### Важные ограничения БД
- `NOT NULL` на `team_id`: разработчик не может существовать без команды.
- Внешний ключ (`FOREIGN KEY`) с каскадом `RESTRICT` или `NO ACTION`: нельзя удалить команду, пока в ней есть разработчики (это поддерживает правило «в команде должен быть хотя бы один разработчик» на уровне БД).
