## ER-диаграмма

>ER-диаграмма (от англ. Entity-Relationship Diagram — диаграмма «сущность-связь») — это графическая схема, 
>которая наглядно показывает, какие данные есть в системе и как они связаны между собой. 

> - `Сущность` (Entity) — это «объект», про который мы храним данные. В терминах БД — это таблица (*collection*, *object*)
> - `Атрибут` (Attribute) — характеристика сущности. В БД — колонка таблицы (*id*, *data*)
> - `Первичный ключ` (PK, Primary Key) — уникальный идентификатор строки. Без него нельзя однозначно обратиться к записи.
> - `Внешний ключ` (FK, Foreign Key) — ссылка на PK другой таблицы. Показывает связь.
> - `Связь` (Relationship) — как сущности «относятся» друг к другу («одна коллекция содержит много объектов»).
> - `Кардинальность` — сколько экземпляров одной сущности связано с экземпляром другой («Один ко многим» (1:N): одна коллекция → много объектов).


## Нотация

С каждой стороны всегда 2 значка: 

- первый - обязательность ( `|` - обязательно, `o` - необязательно)
- второй - количество ( `|` - один, `{` - много)

`||` - ровно один (то есть обязательно)
`|{` - один или больше (обязательно)
`o|` - 0 или 1 (т.е. необязательно)
`o{` - 0 или больше (может быть и 1), необязательно

**Комбинации**:

1. **||--||** — *«одна к одной, обе стороны обязательны».* 
**Пример:** `PATIENT ||--|| MEDICAL_CARD`. У пациента ровно одна медицинская карта, карта связана строго с одним пациентом.

2. **o{--o{** — *«ноль или более к нулю или более».* Связь необязательна с обеих сторон: у каждой сущности может быть 0 или много связей. 
**Пример:**  `ARTICLE o{--o{ TAG`. У статьи может быть 0 или много тегов; у тега может быть 0 или много статей. 
Связь полностью необязательна: можно создать статью без тегов, можно завести тег «впрок», пока ему нечего присвоить.

3. **|{--|{** — *«один или более к одному или более».* Связь точно есть (минимум одна), и может быть много с обеих сторон — это уже «многие ко многим». 
В реляционной БД «многие-ко-многим» напрямую не реализуют — нужна промежуточная таблица.
**Пример:** `TEAM |{--|{ EMPLOYEE`. У каждой команды обязательно должен быть хотя бы один сотрудник (`|{` слева) — пустой команды быть не может.
Каждый сотрудник обязательно числится в какой-то команде (`|{` справа) — не бывает «сотрудника без команды».
Связь реализуется через таблицу `TEAM_EMPLOYEE`, где один сотрудник может быть в нескольких командах, а одна команда — включать много сотрудников.

4. **||--o{**  — *«одна и только одна — ноль или более».* Это типичный вариант “один ко многим”, где родитель обязателен, а детей может не быть: 
**Пример:** `COLLECTION ||--o{ OBJECT`. Слева `||` — объект строго принадлежит одной коллекции; справа `o{` — коллекция может содержать 0 и более объектов.

5. **||--|{** - *"одна и только одна - одна или более".* 
**Пример:**  `PROJECT ||--|{ DEVELOPER`.  В проекте должен быть как минимум 1 разработчик (может быть много).
Символ | у DEVELOPER означает, что разработчик обязан быть закреплён за проектом; статус “без проекта” для активного сотрудника недопустим

6. **o{--|{** - *"ноль или более - одна или более".* Необязательная связь с одной стороны (может быть 0) и обязательная множественная с другой (минимум 1). 
**Пример:**  `CATEGORY o{--|{ ITEM`. Категория может временно не иметь товаров (например, категория в статусе DRAFT может не содержать товаров), но каждый существующий товар обязан относиться к категории.

7. **o|--o|** - *«ноль или один с обеих сторон».* Связь необязательна, но если есть — то ровно одна.
**Пример:** `USER o|--o| PHONE_NUMBER`.  У пользователя может быть 0 или 1 подтверждённый телефон; у телефона — 0 или 1 привязанный пользователь. 

### 1 Обязательная связь "один к одному"

```mermaid
erDiagram
    PATIENT ||--|| MEDICAL_CARD : "имеет"

    PATIENT {
        id 
        first_name
        last_name
        birth_date
        email
    }

    MEDICAL_CARD {
        id
        date_of_creation
        date_of_update
        patient_id
    }
```

**Связь:** `PATIENT ||--|| MEDICAL_CARD : "имеет"`
 
Это строгая связь «один к одному» с обязательностью с обеих сторон:

- **`PATIENT ||`**: каждый пациент имеет ровно одну медицинскую карту в организации (больнице). Нельзя создать пациента без мед.карты.
- **`|| MEDICAL_CARD`**: каждая медицинская карта может принадлежать только одному  пациенту. Недопустимы orphan records (записи-сироты): каждая медицинская карта обязана быть привязана к пациенту.

**Почему это важно для целостности данных:**  
Нотация `||--||` фиксирует бизнес-правило: сущность не существует без своей пары. Это предотвращает ситуации, когда в базе есть «висячие» медицинской карты или пациенты без карты.

**Реализация в физической модели:**
Хотя в ER-диаграмме Mermaid внешний ключ не пишется явно внутри блока атрибутов, связь `||--||` подразумевает наличие обязательного FK. Чаще всего его размещают в таблице «карты», так как карта — это дополнительная информация к основному объекту.

**Таблица: MEDICAL_CARD (реализация связи):**

| Поле | Тип | Ограничения | Описание |
| --- | --- | --- | --- |
| id | INT | PK | Уникальный идентификатор медицинской карты |
| date_of_creation | DATETIME | NOT NULL | Дата создания медицинской карты |
| date_of_update | DATETIME | NOT NULL | Дата последнего обновления медицинской карты |
| patient_id | INT | NOT NULL, UNIQUE, FK → PATIENT.id | Обязательный и уникальный внешний ключ, однозначно связывающий медицинскую карту с пациентом. Гарантирует отношение 1:1 <br>• `NOT NULL` гарантирует, что карта не может быть «бесхозной».<br>• `UNIQUE` гарантирует, что у одного пациента не будет двух  медицинских карт. |

**Ключевые моменты реализации:**
- **`patient_id` как UNIQUE**: это техническое решение, которое превращает связь «один ко многим» (обычный FK) в «один к одному».
- **Обязательность (`NOT NULL`)**: соответствует обозначению `||` в нотации.

**Пример использования в API:**

Такая модель позволяет строить предсказуемые эндпоинты:

- `GET /patients/{id}/medical-card` — возвращает объект medicalCard (200 OK) либо 404 Not Found, если пациента нет. Отсутствие медицинской карты у существующего пациента трактуется как нарушение бизнес‑правила и не должно приводить к ответу 200 OK с пустым телом.
- `POST /patients` — при создании пациента (POST /patients) бизнес-логика требует одновременного создания медицинской карты. Альтернативно — пациент создаётся в статусе DRAFT, а карта должна быть создана до перевода в статус ACTIVE.

**Для разработчика:**

> Поле `patient_id` в таблице `MEDICAL_CARD` является обязательным внешним ключом с уникальным ограничением. Это обеспечивает строгое соответствие один к одному между сущностями `PATIENT` и `MEDICAL_CARD`. В ответах API медицинская карта всегда присутствует как вложенный объект или отдельный ресурс с гарантированным не-null идентификатором пациента. Создание пациента и его медицинской карты рекомендуется выполнять в рамках одной транзакции либо гарантировать атомарность через бизнес-логику, чтобы избежать состояния “пациент без карты”.



### 4 Один ко многим

```mermaid
erDiagram
    USER ||--o{ POST : "пишет"
    CATEGORY ||--o{ POST : "содержит"

    USER {
        id PK
        email
        nickname
    }

    POST {
        id PK
        title
        content
        published_at
    }

    CATEGORY {
        id PK
        name
        description
    }

```
**Связь USER–POST**
Это связь “один ко многим” (||--o{). Один пользователь может иметь ноль или более постов, но каждый пост 
строго принадлежит ровно одному пользователю. Это гарантирует целостность данных: 
пост не может существовать без автора, а автор однозначно определён через внешний ключ user_id.

**Связь CATEGORY–POST**
Здесь тоже связь “один ко многим”. Одна категория может содержать ноль или более постов, 
при этом каждый пост относится ровно к одной категории. Такое решение упрощает фильтрацию по 
категориям на уровне API (например, GET /posts?category_id=...) и позволяет легко строить отчёты “посты в категории”.

```mermaid
erDiagram
    CUSTOMER ||--o{ ORDER : "делает"

    CUSTOMER {
        id PK
        name
        email
    }

    ORDER {
        id PK
        amount
        status
    }
```

>Также связь “один ко многим” (||--o{). В рамках этой модели у одного клиента может быть ноль или более заказов, 
>при этом каждый заказ обязательно принадлежит ровно одному клиенту. Обязательность со стороны заказа (двойные палочки || у CUSTOMER) 
>гарантирует целостность данных: не бывает “бесхозных” заказов без клиента. Для реализации это значит, 
>что в таблице ORDER будет внешний ключ customer_id, по которому легко получить все заказы конкретного клиента 
>(например, через GET /customers/{id}/orders) либо найти клиента по заказу



### 2 Необязательная связь "ноль ко многим" с обеих сторон

``` mermaid
erDiagram
    EMPLOYEE o{--o{ PROJECT : "участвует в"

    EMPLOYEE {
        id PK
        name
    }

    PROJECT {
        id PK
        title
        status
    }
```
	
>Это связь “ноль ко многим” с обеих сторон (o{--o{). В рамках этой модели сотрудник может участвовать в нуле 
>или множестве проектов, а проект может включать ноль или множество сотрудников. 
>Отсутствие двойных палочек (||) означает, что связь необязательна: сотрудник может существовать в системе без привязки к проектам, а проект — без назначенных сотрудников. На практике такую модель используют на ранних этапах или для гибких ролей, 
>когда участие не является обязательным атрибутом сущности

>«В ER-диаграмме показана логическая связь o--o для наглядности, но в реляционной БД “многие ко многим” реализуют через связующую таблицу. 
>Так мы сохраняем нормализацию и можем хранить дополнительные атрибуты связи — например, 
>роль сотрудника в проекте или дату назначения».


### 5 Обязательная связь «один к одному или многим»

```mermaid
erDiagram
    TEAM ||--|{ DEVELOPER : "работает в"

    TEAM {
        id PK
        name
    }

    DEVELOPER {
        id PK
        name
        email
    }
```

**Связь:** `TEAM ||--|{ DEVELOPER : "включает"`

**Описание:**  
Это связь «один ко многим» с обязательным участием с обеих сторон:
- **Со стороны TEAM (`||`)**: каждая команда обязана включать **одного или более** разработчиков. Пустых команд в системе быть не может.
- **Со стороны DEVELOPER (`{`)**: каждый разработчик обязан состоять ровно в **одной** команде. Работа без команды или одновременная работа в нескольких командах невозможна.

**Целостность данных:**  
Обязательность связи обеспечивается на уровне БД через:
- `NOT NULL` для внешнего ключа `team_id` в таблице `DEVELOPER` (разработчик не может существовать без команды).
- Бизнес-правило или триггер на стороне приложения: нельзя создать команду без хотя бы одного разработчика.

**Практическое применение в API:**  
Такая модель позволяет уверенно строить эндпоинты вида:
- `GET /teams/{team_id}/developers` — получить всех разработчиков команды (гарантированно будет хотя бы один).
- `GET /developers/{id}` — в ответе всегда будет поле `teamId`, которое никогда не будет `null`.

**Реализация связи в физической модели**

Хотя на ER-диаграмме внешний ключ не отображается явно, связь `TEAM ||--{ DEVELOPER` подразумевает наличие обязательного внешнего ключа в таблице `DEVELOPER`.

**Таблица: DEVELOPER**
| Поле | Тип | Ограничения | Описание |
| --- | --- | --- | --- |
| id | INT | PK | Уникальный идентификатор разработчика |
| name | VARCHAR(255) | NOT NULL | Имя разработчика |
| email | VARCHAR(255) | UNIQUE, NOT NULL | Email разработчика |
| team_id | INT | NOT NULL, FK → TEAM.id | Обязательная ссылка на команду. Гарантирует, что разработчик всегда принадлежит ровно одной команде |

**Важные ограничения БД**
- `NOT NULL` на `team_id`: разработчик не может существовать без команды.
- Внешний ключ (`FOREIGN KEY`) с каскадом `RESTRICT` или `NO ACTION`: нельзя удалить команду, пока в ней есть разработчики (это поддерживает правило «в команде должен быть хотя бы один разработчик» на уровне БД).
